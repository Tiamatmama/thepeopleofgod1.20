# 时间线事件总线（路线 C：单点收口）设计

- 日期：2026-11-06
- 状态：待评审
- 背景：项目在「记忆 / 情绪 / 自主发言」这一层持续加档位，边际收益递减、复杂度成本递增；
  同时多模块各自维护一份状态（记忆 JSON、Qdrant 索引、情绪、事件簿、私生活档案），
  每加一个功能都要在四五处同步打补丁。本方案换一层做创新：把「状态变更」收成一条只追加的时间线，
  并以它为底座做出新入口「她的一天」。

## 一、目标与非目标

### 目标

1. 提供一个单一职责的事件日志：只负责追加与读取，不认识任何业务概念。
2. 让跨模块通知从「直接调用」变成「追加事件 + 各自订阅」。
3. 以日志为底座做出新读模型「她的一天」，聊天降为其中一种视图。
4. **把「生成」与「投递」拆开**：她可以先产出一个物件（便条 / 半成品 / 疑问），
   再决定什么时候、通过哪个渠道送出去；QQ 只是其中一个投递适配器。
5. **QQ 链路全面接入**：QQ 的收发、主动开口、约定、私生活都进同一条时间线，
   并且她已有的产物有了出口——能主动投递到 QQ，而不只是回复时被动说话。

### 非目标（本方案不做）

- 不做全量事件溯源：记忆的强化 / 遗忘仍然以现有方式修改记忆对象，不改为事件。
- 不把日志变成真相源：第一阶段它只是旁路记录，本地 JSON 仍是记忆的真相源。
- 不引入 Redis / MySQL / 消息队列。
- **不归并网页与 QQ 的身份**：两套记忆键（`qq_<QQ号>_<角色名>__role` 与 `user_<id>__role`）
  仍然各自独立，本方案只让两条链路共用同一套事件机制，不合并记忆档。
- 不回填历史：上线前的旧记忆、旧消息不补写事件，时间线从上线那天开始。
- 不做多实例。

## 二、模块边界

新增 `src/core/timeline.js`，导出 `class TimelineStore`。

接口只有三个：

```js
append(scopeKey, type, payload)        // 追加一条事件，失败抛错
readDay(scopeKey, date, { types })     // 读某一天的某几类事件
listDays(scopeKey, { limit })          // 列出有记录的日期（供入口页用）
```

约束：

- 不导入 memory / emotion / narrator / privateLife 中的任何一个模块。
- 不解析 payload 的业务含义，原样存、原样还。
- scopeKey 由调用方传入，必须是已规范化的键（`<用户>__role` / `<用户>__ai`）。
  本模块不做 normalize，避免把分档语义泄漏进来。

## 三、存储布局

```
data/timeline/<YYYY-MM-DD>/<scopeKey>.jsonl
```

- **按天分片**：读「今天」只打开当天文件，成本与历史总长无关。
- 按 scopeKey 分文件：与记忆档同一套键，便于对齐。
- 只追加，不重写。单行损坏不影响其余行。

选择按天分片的理由：如果按 scope 单文件长期追加，将来做回放时文件会无限增长；
按天切分后「按天重放」天然可行，这是 C 能演化到 A 的前提。

## 四、事件模型

每行一个 JSON：

```json
{ "v": 1, "seq": 137, "at": 1762300000000, "type": "memory.created", "payload": { "mid": "..." } }
```

| 字段 | 含义 |
|---|---|
| `v` | schema 版本，字段变更时按版本分支解析 |
| `seq` | 当天的行序号，读取时按出现顺序编号即可，无需维护计数器 |
| `at` | 毫秒时间戳 |
| `type` | 事件类型，`<domain>.<action>` 形式 |
| `payload` | 业务负载，本模块不解读 |

### 初期事件类型

| 类型 | 触发点 | payload |
|---|---|---|
| `memory.created` | `MemoryModule.storeMemory` 成功记住一条后 | `{ mid, text, scene }` |
| `speech.proactive` | `SystemNarrator` 自主发言成功投递后 | `{ text, trigger, channel }` |
| `appointment.scheduled` | `AppointmentBook` 新增约定后 | `{ id, at, text }` |
| `life.event` | `PrivateLife` 生成一条新动态后 | `{ postId, text }` |
| `message.in` | QQ / 网页收到一条用户消息后 | `{ channel, userId, text }` |
| `message.out` | QQ / 网页发出正式回复后 | `{ channel, userId, text }` |
| `artifact.created` | 她产出一个待投递物件（便条 / 半成品 / 疑问） | `{ artifactId, kind, text }` |
| `delivery.sent` | 物件被投递到某个渠道后 | `{ artifactId, channel, at }` |

写入原则：**日志是决策记录，不是调试日志**。每条事件必须是「系统真的做了这件事」，
宁可漏记也不虚构。

## 五、接入顺序（六刀）

每一刀独立可上线、可回退；任一刀出问题只回退该刀。前四刀只写不改行为，第五刀才新增能力。

1. **第一刀：`memory.created`**
   - 位置：`MemoryModule.storeMemory` 中 `markDirty(key)` 之后
   - 追加是同步 append（不 fsync），耗时在微秒级，不重新引入整档写阻塞
   - 失败只告警 + 计数，不阻断记忆写入

2. **第二刀：`message.in` / `message.out`（QQ + 网页）**
   - 位置：QQ `bridge.js` 的收发必经点、网页 `output.generateOutputAsync` 的收发必经点
   - 只记录，不改动任何行为；QQ 群聊只记管理员与角色的发言，普通成员不入库（控制量与隐私）
   - 这一刀让「她的一天」第一次能看到她在 QQ 里做了什么

3. **第三刀：`speech.proactive`**
   - 位置：`SystemNarrator` 发言投递成功之后统一追加，payload 带 `channel: 'qq' | 'web'`
   - 放在 narrator 内部而不是各端回调里，避免 QQ / 网页各写一遍

4. **第四刀：`appointment.scheduled` / `life.event`**
   - 分别挂在 `AppointmentBook` 新增、`PrivateLife` 新增动态之后

5. **第五刀：`artifact.created` + 投递器**
   - 见第六、七节；**不新增生成调用**，只把已有产物（私生活动态、约定提醒、CIDE 话头）
     重新登记为可投递物件

6. **第六刀：事件驱动调度（先影子模式）**
   - 见第七节「更激进的一步」；影子期只计算不投递，与现有 tick 结果对照后再切换

## 六、QQ 链路接入（二档：观测 + 输出）

QQ 的现状是「只有回复时才会说话」，她的 CIDE、私生活档案、约定簿每天都在产出内容，
但除了被用户问到时，这些内容没有任何出口。二档的核心是**给已有产物一个出口**。

### 6.1 观测（不改行为）

- QQ 键沿用 `qq_<QQ号>_<角色名>__role`，事件写在这个 scope 下
- 私聊：用户消息与角色回复都记 `message.in` / `message.out`
- 群聊：只记「@角色的消息」与角色自己的发言；普通成员闲聊不入库，控制量与隐私
- 主动开口：投递成功后记 `speech.proactive`（已有第三刀覆盖）

### 6.2 输出（新增能力）

- **物件**而非消息：`artifact.created` 的 `kind` 分三类
  - `note`：便条——她想到的一句话
  - `draft`：半成品——没做完的想法、刚写了一半的东西
  - `question`：疑问——她卡住了、想问用户
- **不新增 API 调用**：物件来源复用已有产物
  - `life.event`（私生活动态）→ 可直接作为 `note`
  - 约定到点提醒 → `note`
  - CIDE 产生但被闸门拦下的话头 → `draft`（原本直接丢弃，现在有地方去）
- 用户在 QQ 里回复物件时，回复照常走主链路并记 `message.in`，物件状态随之关闭

### 6.3 投递策略（防止把号玩坏）

| 约束 | 值 | 理由 |
|---|---|---|
| 投递对象 | 仅管理员私聊（沿用现有 `appointmentSessionFilter`） | 不向陌生人/群主动发物 |
| 夜间静默 | 23:00–07:00 不投 | 与现有夜间禁食同一套作息约束 |
| 每日上限 | `QQ_ARTIFACT_DAILY_MAX`，默认 4 | 硬上限，宁可憋着 |
| 同类冷却 | 同一 `kind` 两件之间至少 30 分钟 | 避免连发 |
| 无回应降频 | 连续 2 件无回应，当日上限减半 | 没人理就少说 |

投递是**可失败、可丢弃**的：宁可物件留在时间线里没人看，也不为了送达而突破频次约束。
QQ 号被封是不可逆损失，优先级高于「送达率」。

## 七、生成与投递拆分，以及更激进的一步

### 7.1 拆分

现在 narrator 一个 tick 里同时做三件事：决定要不要说、生成这句话、通过唯一渠道发出去。
拆成两个阶段：

1. **生成**：产出 `artifact.created`（或直接产出要发的文本），写入时间线
2. **投递**：投递器读时间线里未投递的物件，按渠道策略决定发不发、发到哪

收益：

- QQ 变成一个投递适配器，网页收件箱是另一个适配器；新增渠道只写适配器，不改生成逻辑
- 「被闸门拦下的话头」不再直接丢弃，而是以 `draft` 留在时间线里，第二天还能被捞起来
- 生成与投递各自可测：生成不需要网络，投递不需要模型

### 7.2 更激进的一步：调度由事件驱动（影子期先跑）

现有自主发言是 30 秒 tick 轮询：不管有没有事发生，都要醒来判断一次，且每次判断都可能烧一次 CIDE。
改为事件驱动：

- 订阅 `life.event` / `appointment.scheduled` / `memory.created` / `message.in`
- 只有相关事件发生时才评估「要不要说话」；久无事件就完全不评估
- 现有闸门（频率分档、主题饱和、开口前征询、作息）全部保留，只换触发方式

落地方式：**先影子模式**。事件驱动算出的候选写入 `artifact.created`，但不投递；
同时现有 tick 照常工作。对照一段时间后，再决定哪些事件类型可以真正接管。
这样即使事件驱动判断很差，线上体验也不受影响。

## 八、读模型「她的一天」

- 接口：`GET /api/timeline/day?date=<YYYY-MM-DD>`（`date` 缺省为今天）
- **scope 不来自请求参数**：由当前登录会话解析得到，避免客户端伪造键读到他人的时间线
  （`normalizeScopeKey` 对已带 `__role` / `__ai` 后缀的键原样返回，这一点必须在入口处挡住）
- 聚合：读当天全部事件，按时间段分组（凌晨 / 上午 / 下午 / 晚上），
  每类事件映射成一句面向用户的话
- QQ 事件与网页事件混在同一条时间线里，但每条带 `channel` 标记，界面上要能区分
  「她在 QQ 里做了这件事」和「她在网页里做了这件事」
- 未投递的物件单独一栏「她攒着的话」，这一栏是 QQ 输出的来源，也是收件箱的雏形
- 前端：新增独立页面，先不做成聊天页的 tab；入口形态等有真实数据后再定
- 聊天记录暂不进入时间线，留待后续阶段

## 九、失败与一致性

| 情况 | 处理 |
|---|---|
| `append` 失败（磁盘满 / 权限） | 告警 + `timelineFailures` 计数，不阻断调用方 |
| 读到坏行 | 跳过该行 + 计数，全天日志仍可读 |
| 记录写错 | 不回写，追加一条纠正事件 |
| 进程被 kill | 可能丢最后几行（未 fsync），与现有 30 秒合并落盘同一级别 |
| 重复投递 | 以 `delivery.sent` 为准：投递前查当天是否已有同 `artifactId` 的记录，有则跳过 |
| 投递失败（QQ 接口报错） | 不重试超过 1 次，物件留在时间线里；不因为投递失败降级成「无限重试」 |
| 多实例 | **已知前置条件**：当前依赖单进程串行调用，多实例前必须补追加锁 |

## 十、测试

- 单元：`append` / `readDay` 往返、坏行跳过、跨天边界、`seq` 连续
- 集成：调用 `storeMemory` 后，当天日志中必须存在对应 `memory.created`
- 集成：QQ 私聊收发后，当天日志中出现 `message.in` / `message.out`，且 `channel='qq'`
- 投递策略：夜间静默、每日上限、同类冷却、无回应降频逐条覆盖（纯函数，不碰网络）
- 幂等：同一 `artifactId` 重复投递只会产生一条 `delivery.sent`
- 影子模式：事件驱动候选只写 `artifact.created`，不触发任何投递
- 投影幂等：同一份日志计算两次，结果一致
- 回归：现有全部测试保持通过

## 十一、演化为 A（全量事件溯源）的路径

本方案的日志格式是 A 的子集（`v/seq/at/type/payload` 与 A 一致），演化步骤：

1. 把记忆的强化 / 遗忘也表达为事件（`memory.reinforced` / `memory.forgotten`）
2. 让记忆列表从日志投影计算，本地 JSON 降级为快照缓存
3. 向量索引改为从日志重放构建，消除「双写失败导致索引永久缺口」这一类问题

第 3 步有直接实证支撑：当前存在「本地有记忆、云端无向量点」的静默缺口
（曾实测某档 97 条长记忆从未入索引），根因正是记忆有两个真相源。
