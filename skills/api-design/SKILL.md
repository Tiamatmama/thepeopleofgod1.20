# 接口设计

## 何时用
新增模块、对外暴露函数/HTTP 端点、需要确定调用方与被调方之间的契约时。

## 设计次序
1. **先定契约**：参数、返回值、错误形态先写清楚，再写实现。
2. **资源命名**：名词复数表资源，动作用 HTTP 方法。`GET /tasks`、`POST /tasks`、`PUT /tasks/:id`，别用 `/getTask`。
3. **状态码**：200 成功、201 创建、400 参数错、401 未认证、403 无权限、404 不存在、409 冲突、500 服务端错。别一律返回 200。
4. **一致性**：同一系统里成功/失败响应结构保持同一形状（如统一 `{ success, data | error }`）。
5. **分页/过滤/排序**：列表接口一开始就定 `limit`/`cursor`/`sort` 约定，后补代价更大。
6. **幂等与安全**：写操作考虑重复提交；暴露身份与资源归属校验。

## 评审清单
- 命名是否稳定、可读、可复用；有没有泄露内部实现细节到接口。
- 错误信息是否对调用方有用，又不泄露敏感字段。
- 能否在不破坏既有调用方的前提下扩展（加字段而非改字段）。

## 输出格式
`用途` → `契约`（方法/路径/参数/返回/错误，逐条列）→ `边界与取舍`（为什么这么定）。

## 铁律
- 契约一旦定下就当承诺，改动要显式说明是破坏性变更。
- 不为了「通用」提前抽象：只有一个调用方时，别设计万能参数。
